# 第二节　b3（第二个 4-bit）最终结论 —— ★ 定案"三构建"

## 2.1 结论（不迎合、不将就）

**在该环境（vLLM 0.29.0 + compressed-tensors 0.17.0，共享机不允许改版本）下，无法产出可用的第二个 4-bit 实现。**
故 A5-2 扩构建**定案为三构建：AWQ-4bit(b0) + BF16(b2) + FP8(b1)**，b3 空缺并如实披露。

## 2.2 两条路线、三次尝试的完整证据链

**路线 A：bitsandbytes NF4（上级首选）—— 物理不可行**
`vLLM 0.29.0` 的 `QUANTIZATION_METHODS` **不含 `bitsandbytes`**，且
`vllm.model_executor.model_loader.bitsandbytes_loader` 模块**不存在**（`ModuleNotFoundError`）。
⇒ 即使量化成功，**服务栈也读不了**，无法与 b0/b2/b1 同口径起服对比。

**路线 B：compressed-tensors / llmcompressor 官方 oneshot —— 两次尝试均失败**

| 尝试 | 做法 | 失败点（实测原文） |
|---|---|---|
| B1 | 自研 RTN INT4，**零新增安装**，直接用 ct 0.17.0 的 `apply_quantization_config` + 手工 RTN + `ModelCompressor` | 产物**键形与 b0 完全同构**、vLLM 能结构性加载，但 **4B 干跑 39/39 次 `ctok=128` 顶上限 + 输出复读 `'咨咨咨咨…'`** ⇒ **命中"退化即停手"判据**。定位到**失效在打包环节**：`compress_quantized_weights` 落库的 INT4 与我的 RTN 期望值 **16384/16384 精确一致**、ct 自带 `pack_to_int32/unpack_from_int32` 双向恒等=True，但 `ModelCompressor.compress_model` 产物解包后 q 值挤在 `{0,±7,−8}`、round-trip 相对误差 **1.07**（CPU 微模型可复现） |
| B2 | 隔离 venv `--system-site-packages` + **版本匹配**的 `llmcompressor==0.12.0`（PyPI 上**唯一**把 `compressed-tensors` 钉在 0.17.x 的版本）+ `compressed-tensors==0.17.1`（**仅装进 venv**，系统 site-packages 未动）+ 官方 `oneshot(QuantizationModifier, dataset=None, save_compressed=True)` | ① llmcompressor 内部走 `AutoModelForCausalLM`，**无法加载多模态 `Qwen3VLConfig`**（`ValueError: Unrecognized configuration class`）⇒ 改为自行以 `Qwen3VLForConditionalGeneration` 预加载后传模型对象；② 随即 **`ImportError: cannot import name 'GraniteMoeParallelExperts' from transformers.models.granitemoe.modeling_granitemoe`** —— `llmcompressor 0.12.0` 声明 `transformers<=5.10.1`，而系统是 **5.17.0**（已移除该类）。**共享机不允许改 transformers** ⇒ 该路线在本环境**不可用** |

★ 闸门执行情况：**闸门 ①**（隔离 venv 安装）✅；**闸门 ②**（装完先验证系统 vLLM 仍能起服 b0）✅ **已实测通过** ——
`pf_serve_awq4bit_8013.sh` 起服成功、`ctok=7`、`http_err=0`、按 PID 收服、GPU 回 0 MiB；
**闸门 ③**（产出须过非退化冒烟）**未达成**（无有效产物）。
GPU 花费：b3 两次尝试合计 ≈ 6 min（<< 上级给的 1–2 h 上限）。
**未触碰系统 site-packages / vLLM / torch / transformers**（venv 内 `llmcompressor 0.12.0` + `ct 0.17.1`，系统复验为 `vllm 0.29.0 / tf 5.17.0 / torch 2.13.0 / ct 0.17.0`）。

# 第四节　两条入台账的实测偏差

1. **`p4_download.sh` L21 声明 `Qwen/Qwen3-VL-32B-Instruct-FP8` = "19 文件 / 35.53 GB"**
   ⇒ **实测 18 文件 / 35,532,290,088 B（35.532 GB）/ sha `4bf2c2f39c37…`**。
   **字节数与 sha 与声明完全相符，文件数多算 1**。逐件 SHA256 18/18 匹配 HF LFS 元数据 → PASS。
2. ★ **Ampere（SM80）上 FP8 不快反慢**（走 W8A16 反量化，非原生 FP8）：
   **比 AWQ-4bit 慢 ~11.5%（P50 2.12 s vs 1.82 s）、比 BF16 慢 ~18.7%（2.12 s vs 1.71 s）**。
   ⇒ **"多构建"比较的是数值格式的鲁棒性，不是速度**；据此**不得**把 FP8 当作"更快"的构建来叙事。
3. 附带：HF **Xet CAS**（`cas-bridge.xethub.hf.co`）在本机反复 read timeout，速率跌至 **0.3 MB/s**；
   改 `HF_ENDPOINT=https://hf-mirror.com` + **`HF_HUB_DISABLE_XET=1`** 后 **22.5 MB/s** 才下完（23.8 min）。
